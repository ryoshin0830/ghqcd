# issues を加えたリポジトリ検索の実験

問い: README と description に issue の本文を足すと、中国語の質問でリポジトリを見つけやすくなるか。
README で当たっていた質問を壊さないか。

## 結論

**issue を索引に入れると、issue にしか書かれていない内容でリポジトリを探せるようになる。代わりに、README で当たっていた質問が少し崩れる。**

- issue 質問（37 問、中国語・英字なし）の R@1 は、R の 16/37 から R+I で 34/37 に上がった。Top5 は 37/37。
- README がほぼ空のリポジトリ（9 問）では、R の 1/9 が R+I で 9/9 になった。issue を入れる効果が一番大きいのはここ。
- README 質問（19 問）は、R+I で 1〜2 問落ちた（中国語・英字なしは 17/19 → 15/19）。落ちた分はすべて、別のリポジトリが issue の chunk で 1 位を取ったもの。奪ったのは issue の多いリポジトリだった（例: 公開リポジトリの portfolio が、短縮 URL の質問で short-url を抜いた）。
- issue 質問では、日本語（30/37）が中国語（33/37）より低い。日本語の質問は issue の本文と語彙が近く、issue の多いリポジトリの別の issue に引っ張られやすい。日本語で誤った 7 問のうち 3 問は、issue が最も多い（73 件、約 20 万文字）同じ非公開リポジトリが 1 位を取った。
- 正解なしの判定は、R+I のほうが分けやすいように見えるが（残る正解なしが 5/5 → 1/5）、5 問では何も言えない。

**次の一手**: リポジトリの score を「全 chunk の最大値」にすると、issue が多いほど当たりくじが増える。README の score と issue の score を分けて重みを付ける、または issue の chunk に小さな減点をかける、を同じ凍結データで比べるのが安い。

## 限界

- 質問を書いたエージェントは issue を読んでから書いている。言い回しを写さないようにさせ、4 文字以上の一致は機械で検査したが、2 文字単位の一致は残る（全文検索が R+I で 16〜21/37 当たるのはそのため）。実際の利用者が覚えている言葉より、issue に近い質問になっている可能性がある。
- 「答えが一つに決まるか」は、質問を書いたエージェントが判断しただけで、検査していない。
- 中国語はネイティブの確認を経ていない。
- 規模が小さい（49 リポジトリ、issue 質問 37 問、正解なし 5 問）。
- issue のコメントと PR は入れていない。

## 条件

- モデル: Qwen3-Embedding-0.6B（前回の実験で最良）。比較として全文検索（lexical.py と同じ方式）。
- 索引は 2 種類で、同じ質問を両方に投げる。
  - **R**: description + README
  - **R+I**: description + README + issue（タイトル + 本文、open/closed とも。PR とコメントは除く）
- リポジトリの score は、そのリポジトリの chunk の cos の最大値（前回と同じ）。
- 対象: 前回の 26 リポジトリ + issue が 1 件以上ある自分のリポジトリ。
- 質問:
  - **issue 質問**: issue にだけ書かれていて README にはない内容を、別のエージェントが ja / zh / zh_nolatin で書く。原文の言い回しは写さない。
  - **README 質問**: 前回の 19 問 + 正解なし 5 問をそのまま使う。リポジトリが増えた分、前回より難しくなる。

## 非公開データの扱い

issue の大半は非公開リポジトリにある。

- 本文・質問・ベクトル・順位表は `~/Library/Caches/ghqcd-poc/issues/`（0700）に置き、git には入れない。
- この文書と git に載せるのは、件数と正解率などの集計値だけにする。リポジトリ名は公開リポジトリのものに限る。
- 収集のコードには、リポジトリ名を書かない（`gh` で毎回列挙する）。
